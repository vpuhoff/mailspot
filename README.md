# Mailspot

Небольшая почтовая заглушка на Go: принимает SMTP-письма, сохраняет их в SQLite, показывает в веб-интерфейсе и ищет по отправителю, получателям, теме и тексту. Письма наружу не отправляет. Один исполняемый файл, без Redis, PostgreSQL и Node.js.

## Запуск

Через Docker Compose:

```sh
cp .env.example .env
docker compose up -d --build
```

Или локально, с Go 1.26+:

```sh
go build -mod=vendor -buildvcs=false -o bin/mailspot ./cmd/mailspot
RETENTION=72h ./bin/mailspot
```

- Веб-интерфейс: http://127.0.0.1:8080
- SMTP: `127.0.0.1:1025`, без AUTH и TLS.
- Проверка доступности БД: `GET /healthz`.
- Локальная база: `data/mailspot.db`. В Compose используется постоянный том `mailspot-data`.

В тестируемом приложении укажите этот SMTP-хост и порт, отключите авторизацию и TLS. Для другого контейнера в той же Compose-сети адрес — `mailspot:1025`. Остановка: `Ctrl+C` или `docker compose down`; том с письмами сохраняется. `docker compose down -v` удаляет том.

HTTP и SMTP по умолчанию доступны только с локальной машины. Авторизации нет: для доступа из сети нужны ограничения сети или reverse proxy с авторизацией для HTTP. SQLite следует хранить на локальном диске; один экземпляр приложения на одну базу.

## Настройки

Настройки читаются из переменных окружения при запуске. В Compose значения берутся из `.env`; сам бинарник файл `.env` не читает. Для изменения настроек перезапустите процесс или выполните `docker compose up -d`.

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `SMTP_ADDR` | `127.0.0.1:1025` | Адрес SMTP; внутри контейнера `0.0.0.0:1025` |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес веб-интерфейса; внутри контейнера `0.0.0.0:8080` |
| `DB_PATH` | `data/mailspot.db` | Файл БД; в контейнере `/data/mailspot.db` |
| `RETENTION` | `72h` | Срок хранения с момента приёма, независимо от заголовка Date |
| `CLEANUP_INTERVAL` | `1m` | Период очистки; первый проход сразу при старте |
| `MAX_MESSAGES` | `3000000` | Максимум сохраняемых писем после прохода очистки |
| `MAX_MESSAGE_BYTES` | `10485760` | Максимальный размер оригинала: 10 MiB |
| `MAX_BODY_BYTES` | `262144` | Объём декодированного текста для просмотра и индекса: 256 KiB |
| `MAX_CONNECTIONS` | `32` | Максимум одновременных SMTP-соединений |

Длительности: `30m`, `24h`, `168h`; запись `7d` не поддерживается. Все лимиты положительные. Ограничения конфигурации: письмо не более 100 MiB, индексируемый текст не более 10 MiB, не более 1024 SMTP-соединений. HTTP ограничен 64 соединениями; SMTP — 100 получателями на письмо и таймаутами чтения/записи по 60 секунд.

Очистка удаляет сначала просроченные письма, затем самые старые сверх `MAX_MESSAGES`. Срок и число писем — периодически применяемые ограничения: между проходами допускается превышение, большой накопившийся объём удаляется постепенно. Размер диска в байтах отдельно не ограничивается.

## Хранение, поиск и нагрузка

- SMTP возвращает успешный ответ на DATA **после завершения записи** в SQLite. При ошибке хранения возвращает `451`, отправитель должен повторить попытку. При превышении размера — `552`; при исчерпании подключений — `421`.
- SQLite использует WAL, `synchronous=FULL`, одно пишущее соединение и до четырёх читающих. Полные оригиналы, включая вложения, сохраняются в БД. Если SMTP-ответ потерялся в сети, повторная отправка может создать дубликат — дедупликации нет.
- Поиск использует FTS5 с trigram-индексом: подстрока от 3 до 200 символов, без учёта регистра. Спецсимволы запроса обрабатываются как текст. Поиск не сканирует целиком все тела писем через `LIKE '%...%'`.
- MIME-заголовки, base64, quoted-printable и распространённые кодировки декодируются. Индексируются текстовые части `text/plain` и `text/html` в пределах `MAX_BODY_BYTES`; вложения не индексируются. HTML показывается экранированным текстом. При повреждённом MIME исходник остаётся доступен в `.eml`.
- Список выдаётся порциями по 50 писем, без загрузки тел и вложений. Переход к старым письмам использует ID, без растущего OFFSET.
- Очистка удаляет письма и записи поискового индекса транзакциями по 250 строк с паузами для входящего потока. Освободившееся место повторно используется SQLite; incremental vacuum постепенно возвращает свободные страницы файловой системе. Файл не обязан немедленно уменьшаться до размера оставшихся писем.
- SIGTERM останавливает приём новых соединений и даёт активным соединениям до 35 секунд на завершение. Compose ждёт до 45 секунд. Логи Compose ротируются.

**500 писем/мин — 720 000 писем/сутки, 2 160 000 за 72 часа.** Стандартный лимит в 3 млн вмещает 72 часа при 600 письмах/мин. Для оценки диска учитывайте оригиналы, декодированный текст, индекс и WAL: при среднем оригинале 100 KiB только оригиналы за 72 часа при 500/мин займут около 206 GiB. Лимиты размера писем и количества соединений нужно соотносить с доступной памятью; 32 одновременно принимаемых письма по 10 MiB требуют существенно больше памяти, чем обычные маленькие письма.

Краткие проверки не доказывают устойчивость на протяжении нескольких суток. Для проверки на целевом диске и с вашими размерами писем включён отдельный нагрузочный клиент.

Результаты выполненного прогона: [BENCHMARK.md](BENCHMARK.md). При 600 письмах/мин за две минуты принято 1 200 писем без ошибок с одновременным поиском и очисткой.

## API

```sh
# Последние письма: метаданные без тела и оригинала
curl 'http://127.0.0.1:8080/api/messages?limit=50'

# Поиск; параметры следует URL-кодировать
curl --get --data-urlencode 'q=example.test' \
  'http://127.0.0.1:8080/api/messages'

# Следующая страница: используйте next_before из предыдущего ответа
curl 'http://127.0.0.1:8080/api/messages?before=123&limit=50'

# Метаданные и декодированное тело
curl 'http://127.0.0.1:8080/api/messages/123'

# Полное письмо с вложениями
curl 'http://127.0.0.1:8080/messages/123/raw' -o message.eml
```

`limit`: 1–100, по умолчанию 50. Время `received_at` — Unix milliseconds, UTC. `next_before=0` означает пустую страницу; последняя непустая страница может содержать курсор, за которым будет пустая. При переходе по страницам сохраняйте исходный `q`. Поле `truncated` отмечает сокращённый или не полностью разобранный текст.

## Проверки и нагрузочный клиент

```sh
go test -mod=vendor -race ./...
go vet -mod=vendor ./...
go build -mod=vendor -buildvcs=false -o bin/loadtest ./cmd/loadtest

# Две минуты, 600 писем/мин, 8 параллельных клиентов, ~4 KiB/письмо
./bin/loadtest -duration 2m -rate 600 -workers 8 -size 4096

# Трое суток с параллельным поиском каждые 500 мс
./bin/loadtest -duration 72h -rate 600 -workers 8 -size 4096

# Короткая проверка предельной пропускной способности
./bin/loadtest -duration 30s -rate 0 -workers 8 -size 4096
```

Клиент печатает число подтверждённых и неудачных отправок, фактическую скорость, среднюю и максимальную задержки SMTP, ошибки поиска. Завершается с ненулевым кодом при ошибках. Для другой установки задайте `-smtp host:1025 -http http://host:8080`; `-http ''` отключает поиск. Прогон создаёт настоящие тестовые письма, которые занимают место до очистки.

Тесты проверяют конкурентный SMTP-приём одновременно с поиском и очисткой, ограничение размера/подключений, удаление из индекса, кириллицу и MIME, безопасный вывод HTML, сохранение `.eml`, восстановление после открытия базы и отказ подтверждать запись при недоступной БД.

Использованы библиотеки [go-smtp](https://github.com/emersion/go-smtp), [go-message](https://github.com/emersion/go-message) и [modernc SQLite](https://pkg.go.dev/modernc.org/sqlite). CGO для сборки приложения не требуется.
